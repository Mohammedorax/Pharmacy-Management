# تشغيل الأساس التجاري بأمان

هذه النسخة تحتوي نموذج فواتير/دفعات/وصفات/تكاملات جديداً، لكنه **لا يُثبت تلقائياً** عند فتح النظام ولا يملأ دفعات تاريخية من رصيد الأدوية المجمع.

قبل التثبيت:

1. أنشئ نسخة احتياطية SQL Server قابلة للاستعادة، ثم اختبر الاستعادة على قاعدة ينتهي اسمها بـ `_test` أو `_qa` أو `_sandbox`.
2. وجّه إعداد اتصال التطبيق إلى تلك القاعدة الاختبارية فقط.
3. شغّل `project_fo_3.exe --install-commercial-schema "C:\path\verified-backup.bak"` بحساب Windows محلي مسؤول. يتحقق الأمر بـ `RESTORE VERIFYONLY` من النسخة واسم قاعدة الاختبار قبل التثبيت، ولا ينفذ على الإنتاج.
4. بعد تثبيت الأساس فقط، نفّذ `scripts\Apply-CommercialMigrations.ps1` مع `-WhatIf`، ثم شغّله بلا `-WhatIf` لتسجيل/تطبيق الترحيلات الإضافية.
5. لا تبدأ بيعاً بالدفعات قبل إدخال كل دفعة مستلمة برقم تشغيلة وانتهاء وتكلفة حقيقية. لا توجد أي عملية استنتاج تلقائي للأرصدة القديمة.
6. نفّذ سيناريوهات القبول: فاتورة بخصم وضريبة، دفعتان FEFO، مرتجع بإشعار دائن، جرد/استدعاء، واستعادة النسخة.

`FullCommercial` يبقى **مقفلاً افتراضياً**. لا تفعّله في الإنتاج ولا بمجرد تسوية الدفعات: إذا طُلب الوضع التجاري ثم اختلف الرصيد المجمع عن الدفعات، يوقف النظام البيع صراحةً ولا يعود بصمت إلى مسار البيع القديم.

قبل أي تفعيل محدود على قاعدة اختبار، يلزم اعتماد مسؤول تقني لكل ما يلي:

1. تساوي `InventoryLotsTb.QuantityRemaining` مع `MedicineTb1.MedQty` لكل صنف، وتفعيل استلام الدفعات في المشتريات بنفس ترتيب الأقفال ومسار البيع.
2. شاشة بيع تجارية موحدة تعرض وتطبع نفس `Gross / Discount / Tax / Net` المحفوظة في `SalesInvoicesTb`. واجهة البيع الحالية تعتمد سعراً شاملاً بالمعنى المحاسبي القديم؛ لذلك لا تصلح لاختبار ضريبة سعودية حية قبل توحيد نموذج التسعير والتقريب.
3. طباعة وإعادة طباعة من snapshot الفاتورة التجارية، لا من سجل العميل القديم، مع اختبار مستند متعدد الصفحات. تحفظ الفاتورة التجارية الآن بيانات العميل الثابتة وتفاصيل الخصم والضريبة، ويعيد `CommercialInvoiceSnapshotRepository` بناء لقطة الطباعة من الرأس والبنود المعتمدة فقط.
4. إنشاء أثر إلكتروني محلي append-only وOutbox ذري قبل الاعتماد، ثم اختبار جهة الامتثال في بيئتها الرسمية.

ضمن قاعدة الاختبار فقط، يتطلب الأثر المحلي بيانات منشأة حقيقية في `CommercialEInvoiceSettingsTb` (`SellerName` و`SellerVatNumber`) وتعيين `LocalSandboxEnabled = 1`. لا تستخدم قيمة تجريبية أو رقمًا ضريبيًا غير تابع للمنشأة؛ هذا الأثر محلي غير موقّع ويجب أن يظل معلنًا كمحاكاة.

تسلسل الفواتير التجارية يحفظه `CommercialCountersTb` داخل معاملة الاعتماد نفسها؛ لا تغيّره يدويًا ولا تعِد ضبطه، لأن ذلك يكسر قابلية التتبع بين رأس الفاتورة وأثر الـOutbox.

لا تنفّذ تعديل `Mode = FullCommercial` إلا بعد إغلاق هذه العناصر وتوثيق سيناريوهات القبول على قاعدة اختبار قابلة للاستعادة.

مهم: مزود الفاتورة الإلكترونية الموجود محاكي محلياً وغير موقع. لا يتصل بـ ZATCA ولا يمثل امتثالاً أو اعتماداً. تتطلب مرحلة الربط الفعلي شهادات المنشأة، تطبيق مواصفات الجهة المحدثة، والاختبارات الرسمية.

المسار الداخلي للاختبارات الحسابية فقط:

`project_fo_3.exe --verify-commercial-domain`
